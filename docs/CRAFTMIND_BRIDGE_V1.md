# CraftMind ↔ CraftNode Bridge v1

Status: proposal / integration contract. This document does not claim that AI tools are implemented yet.

## Goal

Keep the AI brain (CraftMind) separate from the Android server host (CraftNode), while allowing the two projects to integrate through a small, versioned contract. CraftNode remains the authority for server state and for executing actions.

## Architecture

- **CraftMind**: interprets natural-language requests, explains logs, and proposes structured tool calls.
- **CraftMind provider adapter**: calls a configured AI provider. Provider credentials must never be committed to source control or embedded as a shared app-wide secret.
- **CraftNode bridge**: validates requests, checks supported engine/capability and user confirmation requirements, executes approved operations through existing server controllers, and returns verified results.
- **CraftNode UI**: shows the user's request, any required confirmation, progress, and the result.

Initial integration should be an in-process Android library/API if both projects use compatible Kotlin/Android versions. Keep the contract transport-neutral so a future local service or remote endpoint can be added without changing the tool semantics.

## Contract version

Use `craftmind.bridge.v1`. Reject unsupported major versions rather than silently interpreting them.

### Request

```json
{
  "protocol": "craftmind.bridge.v1",
  "requestId": "uuid",
  "message": "Set the active world to hard difficulty",
  "context": {
    "activeWorldId": "world-id",
    "engineId": "engine-id",
    "serverState": "stopped"
  },
  "allowedTools": ["server.status", "world.get", "world.setDifficulty"],
  "locale": "en-IN"
}
```

Context values are optional hints, not trusted facts. CraftNode must re-read authoritative state before acting. Do not include access tokens, Playit secrets, full environment variables, or unnecessary personal data.

### Tool proposal

```json
{
  "protocol": "craftmind.bridge.v1",
  "requestId": "uuid",
  "kind": "tool_call",
  "tool": "world.setDifficulty",
  "arguments": {
    "worldId": "world-id",
    "difficulty": "hard"
  },
  "requiresConfirmation": true,
  "reason": "Changes a persistent world setting."
}
```

### Result

```json
{
  "protocol": "craftmind.bridge.v1",
  "requestId": "uuid",
  "kind": "tool_result",
  "tool": "world.setDifficulty",
  "status": "success",
  "message": "Difficulty changed to hard.",
  "verified": true,
  "data": {
    "worldId": "world-id",
    "difficulty": "hard"
  }
}
```

Allowed statuses: `success`, `rejected`, `needs_confirmation`, `unsupported`, `failed`, `timeout`. Only report success when the CraftNode controller verifies the resulting state. AI-generated text alone is never proof of success.

## Initial read-only tools

1. `server.status` — running/stopped state, engine and safe resource summary.
2. `server.logs.explain` — explain a user-selected, bounded log excerpt; redact secrets first.
3. `world.list` — list world IDs and names.
4. `world.get` — read supported settings for one world.
5. `players.list` — list currently connected players when supported.

## Controlled write tools (later phase)

Add only when a matching CraftNode controller exists and has tests:

- `server.start`, `server.stop`, `server.restart`
- `world.setDifficulty`, `world.setGameMode`, `world.setCheats`
- `player.kick`, `player.whitelist.add`, `player.whitelist.remove`
- `backup.create`

Write actions must be allowlisted, validate every argument, check engine capability, and request confirmation for destructive, disruptive, or persistent changes. World deletion, arbitrary shell commands, arbitrary file writes, arbitrary downloads, and unrestricted console execution are out of scope.

## Security requirements

- No arbitrary command execution generated by the model.
- No AI-provided path may escape CraftNode's app-owned data directory.
- Validate IDs against the current server/world registry; never trust model-supplied IDs.
- Apply request timeouts and bounded input/output sizes.
- Redact tokens, Playit credentials, and other secrets from prompts, logs, and errors.
- Keep provider keys in user-configured secure storage where possible; do not ship a shared secret in the APK.
- Require explicit confirmation before any tool that changes state. Require stronger confirmation for stop/restart and destructive operations.
- Show the exact action and target to the user before confirmation.
- If an engine does not support an operation, return `unsupported`; never simulate success.

## Error handling

Use structured errors with a stable code and a user-safe message. Preserve technical details only in local diagnostic logs after secret redaction. If the controller cannot verify a change, return `failed` with `verified: false`.

## Implementation order

1. Add this contract and agree on names/types.
2. Create the separate `mechy007/CRAFTMIND` repository with a Kotlin/JVM core and tests; keep Android-specific UI out of the core.
3. Implement the parser/provider interface and tool-proposal data models in CraftMind. Start with a fake provider for deterministic tests.
4. Implement the read-only bridge and tool registry in CraftNode.
5. Connect the chat UI only after the bridge is testable.
6. Add write tools individually, gated by actual engine capability and confirmation.
7. Build the APK and run tests; do not claim live server actions work until tested on-device.

## Acceptance checks

- Unknown protocol version and unknown tool are rejected.
- Invalid arguments and stale world IDs are rejected.
- AI cannot bypass the allowlist or confirmation gate.
- Provider timeout/failure produces a recoverable error.
- Secrets are absent from prompts and logs.
- Success is returned only after the controller verifies the actual state.
- Unit tests run in CI; Android build remains green.
